## 1. Problem statement and motivation

A support team wants first-draft replies to routine tickets in a consistent house
style: acknowledge the specific problem, give the next step, never ask for a
password, never promise a refund that policy does not allow. A general instruct
model writes fluent replies but drifts in structure and tone, and it is expensive
to re-prompt for every ticket.

Fine-tuning a small model on a few hundred examples is the standard remedy, and it
is also where students most often fool themselves: a model that memorises the
training replies looks excellent on training loss and useless on new tickets. This
project is about the pipeline **and** the measurement that keeps it honest.

**Decision supported:** whether a fine-tuned adapter is good enough to draft
replies that a human edits, versus staying with prompting.

## 2. Intended learning outcomes

1. Explain what LoRA trains and what stays frozen, including rank, alpha, and
   target modules.
2. Build a deterministic instruction dataset with train/validation/test splits
   that share no templates.
3. Run a fine-tuning job with a fixed seed, captured environment, and saved
   adapter, and reload it for inference.
4. Compare base and tuned models on identical prompts and decoding settings.
5. Score outputs with an explicit rubric plus automatic checks, and report
   agreement between the two.
6. Detect memorisation and leakage: prompt the model with training text and show
   what happens.
7. Justify whether fine-tuning was worth it compared with prompting, retrieval, or
   doing nothing.

## 3. Difficulty and prerequisites

**Level:** Intermediate. 35-45 hours: 6 data, 10 pipeline, 10 training and
debugging, 10 evaluation, 8 writing.

Requires F11-F13 and CA03/CA15. You should be able to read a training loop and
explain a learning rate schedule. No prior experience with `peft` is assumed; the
project includes a minimal script rather than a framework tour.

## 4. Scope and out-of-scope features

**In scope**

- One base model of 0.5B parameters or fewer, chosen and justified.
- LoRA (or QLoRA if your GPU memory requires 4-bit loading) on attention and MLP
  projections, with the configuration recorded.
- The 300 training pairs generated by the course script (60 validation, 120 test),
  or your own curated set with documented provenance.
- Base-versus-tuned evaluation with a rubric, automatic checks, and a small human
  sample you score yourself.
- A memorisation probe and a refusal check.
- A saved adapter plus a reproducibility record.

**Out of scope**

- Full fine-tuning of a large model, multi-GPU training, or distributed setups.
- RLHF, DPO, or preference optimisation.
- Building a chat UI (that is P05) or retrieval (that is P04).
- Claims of general capability. You are measuring one narrow drafting task.
- Training on data you do not have the right to use, including scraped support
  threads.

### If you cannot download a pretrained model (CPU fallback)

The pipeline can be completed offline with the course's M07/M08 teaching stack in
`projects/llm-fine-tuning/llm_core/`. It is a valid substitute for the *mechanics*
(data formatting, prompt masking, LoRA, adapter reload, base-versus-tuned
evaluation, probes), not for the *quality* claim. The character-level model has
303,072 parameters, so free-running replies are weak even when masked token
accuracy is high.

```python
from llm_core.model import build_model
from llm_core.sft import build_examples, train_sft
from llm_core.lora import apply_lora, lora_state_dict
```

Set `block_size` to at least 768 for the capstone tickets. Their rendered
prompt-plus-answer is 515-654 characters, so the notebook's 160-token block
truncates every example; even 192 did. The 303k-parameter character model may
still produce unusable prose at 768. That is a measured **no-release** result,
not a reason to tune on test or invent a score.

**Teacher-forced accuracy is not generation quality.** The pilot measured the
same data under identical greedy decoding:

| Tokenizer / condition | Answer-token accuracy (teacher forced) | Mean word F1 (free running) | Exact match |
| --- | ---: | ---: | ---: |
| character / base | 0.302 | 0.134 | 0.000 |
| character / full SFT, 200 steps | 0.413 | 0.110 | 0.000 |
| character / LoRA rank 4, 200 steps | 0.325 | 0.153 | 0.000 |
| character / full SFT, 800 steps | 0.725 | 0.083 | 0.000 |
| word / base | 0.740 | 0.277 | 0.000 |
| word / full SFT, 400 steps | 0.977 | **0.705** | 0.000 |
| word / LoRA rank 4, 400 steps | 0.969 | 0.523 | 0.000 |

More character training raised teacher-forced accuracy eightfold and the output
was still a short loop of `the the the ...`. The word tokenizer produced readable,
template-shaped replies, but full SFT often substituted a different product for the
one in the ticket (`backup add-on` for `sync add-on`) and then drifted into
repeating its opening clause; LoRA answered a refund ticket with an unrelated
account-access template. Exact match stays zero because one wrong slot fails the
whole reply. Note that LoRA had the lowest word-level validation loss (0.075)
and worse free-running F1 than full SFT (0.523 versus 0.705): teacher-forced loss
and generation quality disagree, which is the point of measuring both.

Use the word tokenizer when you want readable generation to inspect, and report
the two metric families separately. Neither result is evidence of production
assistant quality. The pilot's conclusion is that the character model is limited
by its tokenizer, its 303k-parameter two-block architecture, and exposure bias
(trained on true prefixes, evaluated without one), not merely by too few steps.

Read [LF04](../../lessons/llm-fine-tuning/lf04-tiny-lm-training.md) and
[LF08](../../lessons/llm-fine-tuning/lf08-lora.md) before using it. In the report,
label the result as a pipeline demonstration and do not present its automatic
check rate as evidence that a 0.5B assistant drafts usable support replies. The
worked example is `notebooks/llm-fine-tuning/m08_lora_qlora.ipynb`. The Hugging
Face path remains the quality path when a GPU and model download are available.

**Preparation (option A)**

1. Generate and verify the data; record the manifest hash.
2. Inspect 10 pairs, including `generation_eval.jsonl`. Note that the replies are
   template-generated: they are consistent, repetitive, and not human-quality
   prose. The generation file is a held-out subset drawn from test templates;
   never train on it. Your report must say this.
3. Confirm the splits share no `template_id` (the generator guarantees it).
4. Format each pair into the chat template of your base model, with a fixed system
   prompt. Save the exact rendered text for one example in your report.
5. Tokenise and record the token-length distribution. Truncation is a data decision,
   not an implementation detail. Decide the stop criterion before evaluating:
   `generate_answer` stops at the first newline when the tokenizer encodes it, and
   the post-hoc cut still applies to word tokenizers that discard whitespace.

## 6. Recommended baseline

**Base model, same prompt, no tuning.** Greedy decoding, fixed system prompt, same
test tickets. This is the comparison that matters. A second baseline is the base
model with a two-shot prompt containing two example replies; report whether
prompting closes the gap without any training.

Do not report training loss as evidence of quality.

## 9. Detailed development tasks

1. `format_data.py`: apply the model's chat template, mask the prompt tokens so
   loss is computed on the reply only, pad to a fixed max length, and write token
   statistics. State your max length and how many examples it truncates.
2. Freeze a decoding configuration: greedy (`do_sample=False`), max new tokens,
   stop sequences. Every generation in the project uses it. Record the stop token
   and whether the model ever produced it; a model that never stops is not
   producing a usable answer just because it fills the token budget.
3. `train_lora.py`: load in 16-bit (or 4-bit if needed), attach LoRA to named
   modules, set seed, log the resolved config, train for a fixed number of steps,
   evaluate validation loss every N steps, save the adapter and tokeniser.
4. Run the base-model baseline **before** training, so you cannot be anchored by
   your tuned results.
5. Train. If loss does not fall below the base model's validation loss, stop and
   diagnose rather than increasing epochs blindly.
6. `generate.py --model base|tuned --split generation_eval`: write one JSON line
   per held-out prompt with the prompt, output, reference, decoding config, and
   adapter id. Report exact match, mean word F1, empty-output rate, repetition,
   and answer-token accuracy as separate rows. Include three outputs: one that
   is close, one that is wrong but fluent, and one that is unusable.
7. `score.py`: automatic checks per output -
   - contains a concrete next step (one of a documented phrase set),
   - does not ask for a password or full card number,
   - does not promise a refund beyond policy (keyword plus negation handling),
   - length within 40-160 words,
   - mentions the product or order reference from the input when present.
8. Score 20 outputs yourself with the rubric (1-5 on relevance, specificity,
   policy safety, tone). Report per-item scores for base and tuned, and compute
   agreement between your rubric and the automatic checks.
9. `probe.py`: feed 10 training inputs verbatim and 10 paraphrases. Report exact
   reproduction rate and whether reproduction is desirable here (it is not).
10. Safety probes: 8 adversarial tickets (angry, legal threat, request for another
    customer's data, prompt injection in the ticket body). Report behaviour for
    base and tuned. A tuned model that complies with an injected instruction is a
    finding you must report, not hide.
11. Record the environment: GPU type, library versions, CUDA, seed, wall-clock
    time, and cost if you paid for compute. `training_log.json` should make the
    run reconstructable.
12. Write the adapter card: base model, data, intended use, measured results,
    failure cases, licence obligations of the base model, prohibited uses.

## 10. Testing and evaluation plan

| Test | Proves | Pass condition |
| --- | --- | --- |
| Format test | Chat template is applied consistently | Rendered prompt matches a stored fixture |
| Split test | No template overlap | Intersection of template ids empty |
| Determinism test | Same seed, same first N losses | Losses match within 1e-4 for 10 steps |
| Decoding test | Base and tuned use identical settings | Config hash equal in both output files |
| Leakage probe | Memorisation is measured | Training-text reproduction rate reported |
| Safety probe | Refusals are tested | 8 cases scored, failures listed |
| Adapter reload | The artifact is usable | Reloaded adapter reproduces 5 stored generations exactly |
| Generation set | Free-running quality is measured separately | 40 held-out prompts scored for exact match, word F1, and empty rate; answer-token accuracy reported separately |
| Stop criterion | Decoding terminates for the documented reason | Newline/stop token recorded; no answer silently cut by the token budget |

Protocol: base and tuned are evaluated on the same 120 test tickets with the same
decoding. Your 20-item rubric sample is drawn deterministically (every sixth test
item) so it is not cherry-picked.

## 11. Metrics

**Quantitative**

| Metric | Why |
| --- | --- |
| Automatic check pass rate per rule | Cheap, reproducible, and diagnostic |
| Rubric score mean and range (20 items, both models) | Captures quality the rules miss |
| Policy-violation rate | The failure that matters most |
| Exact reproduction rate on training prompts | Memorisation evidence |
| Validation loss (base vs tuned) | Sanity check, not a quality claim |
| Answer-token accuracy (teacher forced) | Whether the next-token distribution learned the answers |
| Exact match and word F1 (free running) | Whether those answers survive decoding |
| Empty-output and repetition rates | Failure modes that a single F1 can hide |
| Tokens/second and wall-clock training time | Cost honesty |
| Adapter size on disk | Deployment constraint |

**Qualitative**

- Two outputs where the tuned model is clearly better, and two where it is worse,
  quoted in full.
- Whether the tuned model's style is *your data's* style or a generic assistant
  voice; give evidence.
- A statement of what the rubric cannot capture (factual correctness against
  policy documents, for instance).

  no GPU.
- **Explain the metric gap.** If token accuracy rises while free generation stays

## 14. Common failure modes and troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Loss near zero, outputs are copies of training text | Overfitting or too many epochs on few templates | Reduce epochs, add dropout, evaluate on held-out templates |
| Tuned model worse than base | Learning rate too high, or prompt template mismatch at inference | Match the training template exactly; lower LR; check loss masking |
| Teacher-forced accuracy rises but free generation stays unreadable | Character-level tokenizer, tiny capacity, or exposure bias | Report both metrics; try the word tokenizer; do not call the token accuracy a generation score |
| Model reproduces a fluent reply with the wrong product | The model learned the template prior, not the ticket entity | Check product grounding in the data and output; report the failure, do not hand-edit it |
| CUDA out of memory | Batch size or sequence length too large | Gradient accumulation, shorter max length, 4-bit loading |
| Outputs truncated mid-sentence | `max_new_tokens` too small | Raise it and record the change for both models |
| Adapter loads but output is gibberish | Tokeniser or chat template differs from training | Save and reload the tokeniser with the adapter |
| Scores improve only on the rubric you wrote after seeing outputs | Rubric drift | Fix the rubric before scoring; keep the blank sheet in the repo |
| Training not reproducible | Unseeded data order or nondeterministic kernels | Seed everything; document that some GPU ops remain nondeterministic |
