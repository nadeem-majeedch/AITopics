## 1. Problem statement and motivation

A subscription business loses customers it could have retained. A retention team
can act on a handful of accounts per week: offer a discount, place a support call,
or leave the account alone. The team needs a ranked list of accounts likely to
cancel, with a confidence estimate and a reason a human can check.

This project is the smallest complete machine-learning system in the course. The
model is deliberately simple; the difficulty is in the data handling, the split,
the metric choice, and the honesty of the claims. Every later project reuses this
skeleton.

**The decision this system supports:** which accounts a human reviews this week.
It does not decide who is denied service, and it must never be used to price an
individual account.

## 2. Intended learning outcomes

By the end you can:

1. Turn a business question into a labelled prediction task and state the unit of
   prediction (one row = one customer-month).
2. Audit a table for leakage before modelling, and prove the audit with a
   measured experiment.
3. Build a stratified train/validation/test split and keep the test set unopened
   until the final run.
4. Compare a majority-class baseline, logistic regression, and a gradient-boosted
   model on the same split with confidence intervals.
5. Choose a decision threshold from a cost argument rather than from 0.5.
6. Explain calibration and show a reliability table for your chosen model.
7. Write a model card whose numbers trace to a saved metrics file.

## 3. Difficulty and prerequisites

**Level:** Foundation. Expect 25-35 hours: roughly 6 hours of data work, 8 hours
of modelling, 8 hours of evaluation, and 8 hours of writing and cleanup.

You need F03-F05 and F08-F10. If you cannot explain why a random split can leak
in a table with repeated customers, revisit F05 before starting.

## 4. Scope and out-of-scope features

**In scope**

- Binary churn prediction one month ahead from a supplied feature table.
- Three models: majority baseline, logistic regression, gradient boosting.
- Threshold selection from an explicit cost table.
- Calibration check and a short error analysis by contract type and tenure band.
- A command-line script that trains, evaluates, and writes a report.

**Out of scope (state these in your report)**

- Causal claims ("the discount caused retention").
- Per-customer pricing, credit, or eligibility decisions.
- Real-time scoring, dashboards, or deployment infrastructure.
- Deep learning. A neural network is not an improvement here and will not earn
  marks over a well-evaluated boosted model.
- Uplift modelling or treatment-effect estimation.

Use option A unless you have a specific reason not to. If you use B or C, your
results are not comparable with the course text and you must say so.

**Preparation steps (option A)**

1. `python scripts/make_eval_data.py` writes the corpus and a SHA-256 manifest.
2. Verify it: `python scripts/make_eval_data.py --check`. Record the manifest hash
   in your report.
3. Load the CSV. It ships 1,854 rows and two columns that are recorded **after**
   the outcome: `account_status` (`active`/`cancelled`) and `cancellation_reason`
   (missing for every non-churned row). Do not silently drop them yet - the audit
   step uses them to demonstrate leakage. Record the base rate before modelling.
4. Split 70/15/15, stratified on the target, seed fixed. Save the split indices
   so every model sees the same rows.
5. Run a leakage audit: target-derived columns, duplicate rows across splits,
   and columns that could not exist at prediction time.

## 6. Recommended baseline

**Majority class.** Predict "stays" for every row. Report accuracy, precision,
recall, and the confusion matrix. On an imbalanced target this baseline can look
strong while being useless, which is the first lesson of the project.

**Second baseline:** logistic regression on standardised numeric features with
one-hot categoricals. If your boosted model cannot beat it by a margin larger than
the confidence interval, report that and keep the simpler model.

## 9. Detailed development tasks

1. Write `prepare.py`: schema check (column names, dtypes, ranges), target
   encoding, category handling, and a saved split file. Fail loudly on unexpected
   columns instead of silently coercing.
2. Write `audit.py` with three checks: (a) any feature with correlation above
   0.98 to the target, (b) duplicate feature rows appearing in more than one
   split, (c) features whose values are only known after the outcome. Print a
   table and exit non-zero if a check trips.
3. Demonstrate the leak on purpose: train once with `account_status` and
   `cancellation_reason` included. `account_status` maps one-to-one onto the
   target, so the score should be near-perfect. Record it, then remove both columns
   and retrain. Keep both numbers in the report; they are the evidence that your
   audit works. Also test `cancellation_reason` alone, where the missingness rather
   than the value carries the signal.
4. Train the majority baseline and logistic regression. Save predictions, not
   just scores, so later analysis can reuse them.
5. Train a gradient-boosted model. Tune at most three hyperparameters on the
   validation split. Do not touch test until milestone 4.
6. Build the cost table: cost of a false negative (lost account) versus a false
   positive (wasted retention offer). Derive the threshold that minimises expected
   cost, and show precision, recall, and the confusion matrix at that threshold
   next to the 0.5 threshold.
7. Compute bootstrap confidence intervals for accuracy and ROC AUC on the test
   set. Use at least 1,000 resamples and report the interval, not just the point.
8. Produce a reliability table (10 bins: mean predicted probability versus observed
   rate) and the expected calibration error.
9. Slice the test set by contract type, tenure band, and region. Report the metric
   and the number of rows in each slice. Flag any slice with fewer than 30 rows as
   too small to interpret.
10. Write `report.py` so the report is generated from `metrics.json`. Hand-edited
    numbers in prose are how invented results happen.
11. Write the model card: intended use, training data, metrics with intervals,
    calibration, known failure slices, and prohibited uses.
12. Clean rerun: delete `outputs/`, run the pipeline end to end, confirm the same
    metrics appear (allow bootstrap noise, not changes in the point estimates).

## 10. Testing and evaluation plan

| Test | What it proves | Pass condition |
| --- | --- | --- |
| Schema test | Your loader rejects bad input | Adding a column with 40% missing values raises a clear error |
| Split disjointness | No row appears in two splits | Intersection of row hashes is empty |
| Leakage regression | The audit catches a known leak | Synthetic leak column trips the audit and inflates the score |
| Determinism | Reruns agree | Two runs give identical point estimates at a fixed seed |
| Threshold test | Cost logic is implemented, not guessed | Changing the cost ratio moves the threshold in the expected direction |
| Metric unit test | Your metric code is correct | Hand-computed 8-row example matches, and matches scikit-learn |

Evaluation protocol: one test-set evaluation for the final model, plus the
deliberate leak experiment reported separately. If you evaluate on test more than
once while choosing between models, say so and treat the test set as validation.

## 11. Metrics

**Quantitative**

| Metric | Why | Reported as |
| --- | --- | --- |
| ROC AUC | Ranking quality, threshold-free | Point + 95% bootstrap interval |
| PR AUC / average precision | Honest under class imbalance | Point + interval |
| Precision, recall, F1 at the chosen threshold | Operational meaning | With the threshold stated |
| Expected cost per 1,000 accounts | Ties the model to the decision | Using your stated cost table |
| Expected calibration error | Whether probabilities mean anything | 10-bin table plus ECE |
| Accuracy | Comparability with the baseline | Include the majority baseline next to it |

**Qualitative**

- Two or three concrete accounts the model gets wrong, described in plain language.
- Whether the top-ranked accounts look plausible to a domain reader, with the
  caveat that you are not a domain reader unless you say why.
- A statement of what the model cannot know (life events, competitor offers).

**Do not** report a single accuracy number as the headline. On this task it is the
least informative metric available.

## 13. Suggested extensions

- Add a cost-sensitive learning variant (class weights or sample weights) and
  compare it with threshold tuning at the same expected cost.
- Add a simple monotonic constraint or an explainable surrogate and check whether
  explanations match the model's behaviour on the top 20 accounts.
- Simulate a monthly retrain and measure how the chosen threshold drifts.
- Replace the churn label with a 60-day horizon and report how the base rate and
  the achievable AUC change.

## 14. Common failure modes and troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| AUC near 0.99 | A column derived from the target survived the audit | Rerun the audit; check every column's availability timestamp |
| Accuracy high, recall near zero | Threshold at 0.5 on imbalanced data | Choose the threshold from the cost table |
| Train score much higher than validation | Overfitting or leakage across splits | Check duplicate rows and grouped structure; simplify the model |
| Probabilities cluster at 0 and 1 | Uncalibrated boosted model | Report calibration; consider Platt scaling fitted on validation only |
| Metrics change on every run | Unseeded split or model | Fix seeds for split, model, and bootstrap; record versions |
| Report numbers disagree with `metrics.json` | Numbers typed by hand | Generate the report from the metrics file |
| `--check` fails on the data manifest | Regenerated data with a different seed | Re-run the generator at the documented seed and record the new hash |

Use the shared [report template](report-template.md) with these project-specific

## 18. Demonstration and presentation checklist

Eight minutes, screen shared, no slides required beyond four.

- [ ] Show the rerun command and the manifest hash (30 s).
- [ ] Show the audit tripping on the leak column, then passing (90 s).
- [ ] Show the metrics table with intervals and the majority baseline (60 s).
- [ ] Show one account the model ranks high, and explain why in plain language (60 s).
- [ ] Show one failure slice and what you would do about it (60 s).
- [ ] State two limitations and one prohibited use (45 s).
- [ ] Answer: "What would you need before this touched a real customer?" (rest).

**Common demo mistakes:** showing only the best metric; claiming causation;
answering "the model is 87% accurate" when the base rate is 73%; having no answer
for what happens when the model is wrong.
